## 2. Nonnegotiable requirements and source precedence

### 2.1 Authority order

1. **Primary:** `DSX-project-plan(1).md` sections 0-14, especially §§2, 4-7, and 5.9.
2. **This spec:** an implementation-level expansion of the primary source. It deliberately resolves ambiguities and names corrections; its new conventions are marked **IMPLEMENTATION DECISION**, not falsely attributed to the source.
3. **Secondary:** `thpfqbq.md` provides reusable design ideas: typed contracts, one composition root, strict import boundaries, stable deterministic scenarios, Pydantic validation if useful, cached Streamlit runs, and tests. **Do not import its alternate epidemiology, hospital, FDNA, and rerouting equations.**
4. **External documentation:** for current Kiro capabilities, the original FDNA paper, and historical-dataset status, not permission to silently rewrite the hackathon plan.

### 2.2 Invariants that must remain true

- Exactly nine conceptual blocks in order: `DATA -> SEPARATE -> IL1 -> SEIR -> IL2 -> FDNA -> ANALYSIS -> IL3 -> RESULTS`.
- Exactly **one simulated week per pipeline iteration**, with **seven daily numerical substeps inside SEIR** if useful. A `week` is NOT a `day`, and its UI labels are not interchangeable.
- Districts = **census tracts** by default; study region = **Suffolk County** by default; extending the region is a config choice.
- Hospitals and districts are the only **default FDNA node types**. Staff, oxygen, EMS, ICU, wards, and mortality feedback are future work, not P0.
- Directed FDNA feeder -> receiver edges: hospital -> district; symmetric two-way hospital <-> hospital; **no district -> hospital FDNA edges**. District cases affect hospital *load*, not FDNA edge direction.
- One accessibility/share function is reused by epidemic patient placement and district FDNA dependence. Rerouting changes actual flow **without silently modifying the base accessibility shares**.
- Hospital own score derives from total load and capacity. FDNA propagates degradation. ANALYSIS reassigns epidemic patients only if candidate hospitals have spare effective capacity.
- Scenarios are explicit injections applied by week, logged and reproducible. Baseline scenario and intervention scenario must not mutate each other's state.
- No access to patient-level records. No live API requirement in the judging demo. Every numeric assumption appears in config and is labeled.
- The dataset, method, temporal holdout, actual validation MAE (in beds), and persistence MAE are displayed only after they have been computed. Never promise a win over baseline.
- Frontend uses **Streamlit**, with **pydeck or folium** for maps, not a new React/FastAPI stack unless the team deliberately changes the primary plan after the hackathon.

### 2.3 Explicitly NOT in scope for v1

The secondary document proposes age-by-patch coupled SEIR; daily `xarray` state; ward/ICU accounting and ICU deaths; bed-buffer, staff-pool, oxygen and EMS resource nodes; automatic formal diversion hysteresis; volume-over-capacity patient placement; topological-only FDNA; and a separate diversion signal to tomorrow's allocation. These are **not** the v1 architecture. Some may be used later behind new interfaces, but using them now would break the weekly contracts and change scientific claims.

## 3. Product definition and end-to-end behavior

**Working name:** "ResiliNet | Boston Hospital Cascade". The name is UI branding only; the primary plan describes the mechanism rather than requiring a particular brand. Display "Research simulation - not for emergency planning" prominently.

**User:** A DS+X judge, researcher, or curious Boston resident who wants a demonstrable and transparent what-if answer, not a hospital planner making real patient-routing decisions.

**Primary interaction:**

1. App loads a reproducible baseline with region, district boundaries, hospitals, time range, configs and provenance.
2. User chooses week `t`. Baseline SEIR produces district hospital census `H_j(t)` and weekly new admissions, clearly distinguished.
3. IL2 applies base district -> hospital shares and computes each hospital's total demand, effective capacity, own score and FDNA graph.
4. FDNA solves hospital dependency effects, then computes a 0-100 district access score.
5. App renders **before rerouting**: stressed hospitals, district access, excess beds and district-level access indicators.
6. ANALYSIS tries to move the *epidemic occupancy allocated to overloaded hospitals* into spare hospital beds; it cannot teleport normal patients out of an already full/closed hospital. It recomputes hospital load, FDNA scores and district access.
7. User switches to **after rerouting** for the exact same week and scenario; comparison states the change in unmet demand, hospitals' scores and districts' scores.
8. User adds an injection (e.g. hospital closes starting week `t`, hospital capacity factor 0.6). App reruns cleanly from week 0 or otherwise respects all earlier carried state, with the chosen injection starting only on its requested week.
9. Optional paired scenario view compares `baseline` versus `intervention`, with the same disease trajectory and the same data assumptions.
10. Data/validation section reports a historical test if available; otherwise explicitly says it is **not validated** and does not display fictitious metrics.

**The user should be able to answer:** "Which hospital is overloaded?", "How many epidemic beds were moved?", "How many people remain without modeled bed capacity?", "Which tracts lose modeled access?", "Is this observed or a simulation?", and "Did the model predict real occupancy better than simply assuming next week equals this week?"

### 3.1 Functional acceptance criteria (EARS style)

- WHEN valid processed data/config are supplied, THE SYSTEM SHALL produce a deterministic `RunResult` with exactly one `WeekResult` per requested week.
- WHEN a district has a reachable hospital, THE SYSTEM SHALL assign base patient shares summing to 1 within numerical tolerance.
- WHEN a hospital is closed, THE SYSTEM SHALL set effective capacity and its own score to zero; rerouting SHALL NOT send additional epidemic occupants to that closed hospital.
- WHEN rerouting occurs, THE SYSTEM SHALL preserve each district's total epidemic occupancy, except that occupants not served remain explicitly **unmet**, not erased.
- WHEN the same week is rendered before and after rerouting, THE SYSTEM SHALL NOT advance SEIR time or change the disease state between the two views.
- WHEN an injection begins at week 4, THE SYSTEM SHALL leave weeks 0-3 exactly unchanged versus the baseline (assuming no other scenario difference).
- WHEN a dataset is synthetic, THE SYSTEM SHALL label the entire run `SYNTHETIC / ILLUSTRATIVE` in the UI, exports and README.
- WHEN validation data are missing, THE SYSTEM SHALL render `Validation unavailable - no observed holdout loaded` rather than an arbitrary MAE or a success check.
- WHEN a parameter changes, THE SYSTEM SHALL build a new run from its complete immutable config; cached results SHALL be keyed by content and not reused incorrectly.
- WHEN inputs violate a contract, THE SYSTEM SHALL produce an actionable validation error rather than silently dropping rows or silently fixing probabilities.

## 4. Architecture and repo layout

### 4.1 Single-source dataflow

```text
             REPRODUCIBLE LOCAL INPUTS                ONE-WEEK SIMULATION LOOP
  data/raw + provenance + crosswalk
                 |                                  +------------------------------+
                 v                                  |                              |
             [1 DATA]                               |                              |
                 v                                  |                              |
           [2 SEPARATE] -> district + hospital tables                              |
                 v                                  |                              |
             [3 IL1] <------ SEIR state from previous week [8 IL3] <-------------+
                 v
             [4 SEIR]  (7 daily integration steps internal; weekly outputs)
                 v
             [5 IL2] <- disease H, hospitals, geography, week injections
                 |  --> fixed shares, candidate graph, own scores
                 v
             [6 FDNA] --> before hospital/district scores
                 v
           [7 ANALYSIS] --> greedy rerouting -> recompute IL2 load + FDNA -> after
                 |             ^
                 |             +--- scenario injection rerun, not a second epidemic week
                 v

                 v
             [9 RESULTS] --> Streamlit map, charts, table, validation, downloadable run
```

Workers implement their own modules against published shared contracts.

### 4.3 Dependencies and anti-patterns

- `pipeline/contracts.py` and `pipeline/config.py` contain only types, pure validation helpers, and common errors. They should NOT import Streamlit or other pipeline stages.

- `validation` may call the public simulation API for testing/fit and may access documented model observables, but not monkey-patch internal state.
- `app` calls `pipeline.api` ONLY, receives frozen results, and performs presentation transformations only. A UI callback cannot secretly implement FDNA math.
- No global mutable model object; no reused SEIR solver or previous-run patient flow across different scenarios.
- Do not add an API server, database, log-in/auth, payment service, LLM calls, live hospital API, or production emergency-dispatch integrations.

## 5. Implementation contracts and data types

All stage inputs/outputs must be **typed and validated**. Use Python `dataclass` / `TypedDict` / Pydantic models consistently; the concrete representation is an implementation choice frozen by the architect before delegation. Arrays are ordered by stable sorted district/hospital IDs; all views must carry explicit IDs and cannot rely on silently reordered pandas rows. Array indexes are internal; serialized results use named columns/IDs.

### 5.1 Contracts: entity schemas

| Name | Mandatory fields | Units / constraints | Provenance |
|---|---|---|---|
| `District` | `district_id`, `geometry`, `centroid_lat`, `centroid_lon`, `population`, `risk_weight`, `ej_flag` | GEOJSON WGS84 geometry; population >0; risk_weight >=0; EJ true/false/unknown | census geometry, ACS, optional CDC PLACES/EJ |
| `Hospital` | `hospital_id`, `name`, `lat`, `lon`, `staffed_beds`, `icu_beds`, `baseline_occupancy` | coords valid; staffed beds >0; ICU beds >=0; **baseline_occupancy = occupied baseline BED COUNT**, not a percentage | MassGIS/CMS, HHS, assumption if needed |
| `DiseaseConfig` | `r0`, `latent_days`, `infectious_days`, `p_h`, `los_days`, `initial_infectious_fraction`, `seir_mode` | days >0; r0>0; p_h in [0,1]; seed in [0,1]; mode `A` default | fitted/assumed tags |
| `NetworkConfig` | `d0_km`, `k_nearest`, `radius_km`, `hospital_link_radius_km`, `alpha_d`, `alpha_h`, `beta_h`, `distance_shape` | >0 radii/d0; positive integer k; alpha [0,1]; beta [0,100] | assumption tags |
| `SEIRState` | `week`, `district_ids`, arrays `S,E,I,R,H` | units **people**, shapes `[district]`; sum to N; nonnegative | propagated model state |
| `SEIRWeekOutput` | `state_end`, `new_admissions`, `new_infections`, `week` | people per **week**, NOT occupancy; arrays `[district]` | integral of model transitions |
| `Accessibility` | `district_ids`, `hospital_ids`, `distance_km`, `eligible`, `a`, `shares`, `total_accessibility` | arrays `[district,hospital]` except total `[district]`; shares sum 1 for each district | geographic calculation |
| `Flow` | `district_id`, `hospital_id`, `base_share`, `patients` | `patients` = epidemic *occupancy* people for this week, not new admissions | IL2 |
| `HospitalLoad` | `hospital_id`, `epidemic_demand`, `baseline_demand`, `total_demand`, `effective_capacity`, `own_score`, `excess` | people/beds, score 0-100; each unit documented | IL2 |
| `Edge` | `feeder`, `receiver`, `kind`, `alpha`, `beta` | kind `hospital_hospital` or `hospital_district`, bounds; endpoint exists | IL2 graph |
| `Injection` | `injection_id`, `kind`, `target_id(s)`, `value`, `start_week`, `end_week`, `note` | start >=0; `end_week` EXCLUSIVE or null; kind-specific constraints | user's explicit scenario |
| `FDNAResult` | `hospital_scores`, `district_scores`, `iterations`, `converged`, `max_delta` | ordered IDs and scores [0,100]; convergence diagnostics | FDNA |
| `RerouteRecord` | `week`, `district_id`, `from_hospital`, `to_hospital`, `patients` | moved >=0; strictly reachable candidate | ANALYSIS |
| `WeekResult` | `week`, `state`, `before`, `after`, `reroutes`, `unmet_by_district`, `baseline_unmet_by_hospital`, `active_injections`, `diagnostics` | before/after same epidemiological week; no hidden recompute | IL3 |
| `RunResult` | `run_id`, `data_mode`, `config`, `weeks`, `validation`, `data_manifest`, `warnings` | deterministic run identifier; `validation` may be null/unavailable | API |

`data_mode` must distinguish at least `historical_data`, `mixed_assumptions`, `synthetic_demo`. Even with real historical hospital data, future scenario trajectories and uncalibrated behavior are **simulated**, not observed. Every provenance record should be specific per field when possible.

### 5.2 Stage signatures and exact ownership

The following signatures describe required **interfaces**, not code to paste as a finished implementation. Kiro should generate actual typed Python functions and corresponding unit tests.

```text
DATA:        load_raw(manifest) -> RawBundle
             validate_raw(raw) -> DataDiagnostics
             save_clean(clean, destination) -> Manifest
SEPARATE:    build_districts(raw, config) -> DistrictTable
             build_hospitals(raw, crosswalk, config) -> HospitalTable
             check_separation(districts, hospitals, config) -> Diagnostics
IL1:         init_state(districts, disease_config) -> SEIRState
             carry_state(previous_state) -> SEIRState
             check_il1(state, districts) -> Diagnostics
SEIR:        step_week(state, disease_config) -> SEIRWeekOutput
             check_seir(output, districts) -> Diagnostics
ACCESS:      build_accessibility(districts, hospitals, network_config) -> Accessibility
IL2:         compute_flows(H_by_district, accessibility, injection_overrides) -> FlowTable
             compute_own_scores(flows, hospitals, capacity_overrides, score_overrides) -> HospitalLoad
             build_graph(hospitals, districts, accessibility, injection_overrides) -> FDNAGraph
             apply_injections(base_inputs, injections, week) -> ScenarioInputs
             check_il2(...) -> Diagnostics
FDNA:        solve_hospitals(own_scores, hospital_edges, settings) -> HospitalScores
             solve_districts(hospital_scores, shares, network_config) -> DistrictScores
             check_fdna(...) -> Diagnostics
ANALYSIS:    find_overloaded(hospital_load) -> List[HospitalID]
             reroute(base_flows, capacities, hospitals, shares, eligibility, settings) -> RerouteResult
             summarise(before, after, reroute_result) -> WeekSummary
             compare_runs(run_a, run_b) -> ScenarioComparison
             analysis_hook(context) -> Optional[Proposal]   # default no-op
IL3:         package_results(...) -> WeekResult
             next_state(seir_output, active_injections) -> NextWeekInput
             export_results(run_result, format) -> bytes/path
API:         load_run_inputs(config_path, data_root) -> ValidatedInputs
             run_scenario(validated_inputs, injections) -> RunResult
             compare_scenarios(base_inputs, injection_set) -> ComparisonResult
             get_validation_report(...) -> Optional[ValidationReport]
```

**Important:** `run_scenario` must return both before/after rerouting for each week, with all data from one canonical pipeline. Never create a separate “UI-only” computation of those results.

Do not silently assign to a hospital outside the declared catchment unless an explicitly documented fallback flag is enabled.

## 8. IL1 and SEIR: epidemic state and fitting

### 8.1 Precise SEIR + hospitalized box

The primary plan calls this "SEIR" while adding `H`. The minimal scientifically coherent transition model is **S -> E -> I -> R**, with a fraction of departures from I routed through `H` before R:

```text
beta  = R0 / infectious_days               # because gamma = 1/infectious_days
sigma = 1 / latent_days
gamma = 1 / infectious_days
eta   = 1 / los_days

infection_rate(t)  = beta * S(t) * I(t) / N
exposure_to_I(t)  = sigma * E(t)
leaving_I(t)      = gamma * I(t)
new_hospitalizations_rate(t) = p_H * leaving_I(t)
discharge_rate(t) = eta * H(t)

dS/dt = -infection_rate
dE/dt =  infection_rate - exposure_to_I
dI/dt =  exposure_to_I - leaving_I
dH/dt =  p_H * leaving_I - discharge_rate
dR/dt = (1 - p_H) * leaving_I + discharge_rate
```

Then `d(S+E+I+R+H)/dt = 0`. As each patient exits the infectious compartment they either enter H or R, and a hospitalized patient later enters R. This addresses a dangerous implementation mistake: **do not count hospitalized people simultaneously in I and H** if checking compartment conservation. We explicitly assume people admitted from I are removed from infectious community mixing. Deaths are not separately tracked in v1.

- **`H_j(t)` is a snapshot of occupied epidemic hospital beds**, in people, at the end of a week.
- **`admissions_j(t)` is the *integral* of pH * gamma * I over that week**, in newly hospitalized people/week.
- **`new_infections_j(t)` is the integral of the infection rate over that week**, in new infections/week.
- Do not use `admissions` in place of H for `flow_ij` because that loses patients admitted in earlier weeks who have not left the hospital.
- Do not naively sum weekly admissions to compute census without discharges.
- Seven daily substeps, with an ODE integrator such as `scipy.integrate.solve_ivp`, are permitted internally. A stable 7-day stepping implementation must keep all compartments nonnegative within explicit tolerance and conserve N; record numerical error. If using explicit Euler, demonstrate a sufficiently small step or use bounded event flow to avoid negative populations.

### 8.2 Default Option A: ONE shared regional epidemic curve, district outputs

The primary plan says **"One SEIR curve, split by district"** as the hackathon default, while elsewhere saying per-district states sum to each district's population and `risk_weight` adjusts hospitalization. Naively distributing every infection with a population*risk proportion can violate local mass conservation or confuse chronic disease risk with infection risk. The following is an **IMPLEMENTATION DECISION** to make Option A valid and fast without inventing mobility data:

1. All districts share the **same normalized S/E/I epidemic trajectory** (same `r0`, latent period, infectious period, infection seed fraction). There is no geographic transmission wave and **no between-district infection coupling**.
2. Multiply the normalized S/E/I values by each district's population to obtain district-specific counts. Epidemic infection incidence is proportional to population by default.
3. Each district has an independent hospitalization risk `p_H_j = clip(p_H * risk_weight_j, 0, 1)`; derive its own H/R split from that shared I exit flow and its own H discharge. Hospital census and admissions therefore vary with risk weight, while S/E/I remain on the one common epidemic curve.
4. Enforce `S_j + E_j + I_j + R_j + H_j = N_j`, nonnegative values, with R_j computed from the actual transition equations, not assigned as an arbitrary residual that could become negative.
5. Fit the shared disease parameter(s) to **aggregated** observed occupancy and report that the model does not infer district-level infection curves from scarce hospital data.

**Disclosure:** This differs in one important respect from the primary plan's shorthand "split weekly infections by population × risk_weight". For model safety, `risk_weight` is applied to *hospitalization* rather than the chance of infection, consistent with its original definition. A future explicit option may reproduce an infection-risk-weighted allocation with a physically coherent population-conserving scheme, but do not silently claim it is already implemented. Mark this decision in `docs/assumptions.md`.

### 8.3 Optional Option B, deliberately deferred

Option B is a metapopulation per-district SEIR with distance-decaying mixing:

```text
lambda_j = beta * (I_j + sum_{k != j}(mix_jk * I_k)) / N_j
```

The source explicitly calls B an optional upgrade to start **only if A is finished early**. Mixing coefficients are unknown and would be assumptions, not data-based transmission evidence. B must export exactly the same weekly `SEIRWeekOutput` contract. Do not begin it during the MVP or validation build.

### 8.4 Initial and carried state

Week `0`: `I_j = seed_fraction * N_j` by default, `S_j = N_j - I_j`, `E_j=H_j=R_j=0`. If a configurable seeded district is allowed, clearly label that as an alternative scenario whose regional prevalence differs from Option A's uniform initial curve.

At week `t+1`: use precisely `state_end` from week `t`, including H and R. Rerouting moves where modeled patients are served; **it never changes how many residents of a district are hospitalized**, so rerouting may not alter the returned SEIR state. Injections do not feed back into infections or recovery in v1.

### 8.5 Parameter fitting (real science, not a slider performance trick)

- Fit `R0` initially; fit `p_H` *only if it can be identified with the available data*. The two often trade off with scale/timing; adding arbitrary free variables can create a deceptively good fit.
- Choose historical window and reporting variable only AFTER real data have been inspected. Prefer a period with consecutive observed weeks, multiple hospitals with reliable IDs, and clear admissions/occupancy semantics.
- Training objective: least squares on the *observation-compatible* model output for the TRAINING period (COVID-specific modeled served occupancy when the target is COVID-only occupied beds; baseline-served + epidemic-served when the target is total occupied beds), with historical week aggregation matched to the source. Regional raw H is a demand proxy and must not silently substitute for a capacity-constrained occupied-bed target. If capacity effects are negligible, document why modeled demand and served occupancy coincide.
- Fit seed/init condition only with explicit permission in config, record the optimization bounds and random seed (if stochastic optimization is used).
- Validate capacity and population consistency. Report train and test start/end dates, count of weeks/hospitals, missing exclusions, fitted parameters and optimizer warnings. Report confidence intervals only if actually computed.
- The model may be wrong or worse than the persistence baseline. Do not change validation mode or hide results to avoid this finding.

**SEIR tests:** zero epidemic seed -> zero epidemic admissions; disease transitions conserve population; hospital admissions nonnegative; `H` decreases with no new admissions; 7-day step boundary continuity; changing `p_H` affects hospitalization load but not the shared infection curve in Option A; `risk_weight=1` yields identical normalized curves across districts; rerouting leaves next week's disease state unchanged.

## 9. Accessibility and hospital catchment shares

The purpose of a shared `build_accessibility(...)` is to make **patient allocation and district dependency identical at baseline**.

For district `j`, hospital `i`, distance `d_ji` in kilometers, distance decay scale `d0`:

```text
Exponential (default):          a_ji = exp(-d_ji / d0)
Inverse-square (optional):       a_ji = 1 / (1 + (d_ji / d0)^2)
Eligibility:                     hospitals within radius R, keep nearest k
Base share (eligible only):      s_ji = a_ji / sum_h(a_jh)
Total absolute accessibility:    A_j  = sum_h(a_jh)
```

- Noneligible hospital gets `a=0` for normalization, `share=0`, and no hospital -> district FDNA edge.
- `sum_i s_ji = 1` (within tight numerical tolerance), for each district with at least one eligible hospital.
- `A_j` is an *uncalibrated accessibility index* based on a distance kernel, not a percentage of the population with access, not a travel time and not an observed healthcare accessibility statistic.
- Use stable tie-breaking by `(distance, hospital_id)`; never depend on unpredictable row order.
- A district with one eligible hospital has share=1; one of four equally distant hospitals has share=0.25; the failure criticality relation must use this same share.
- Default catchment policy remains based on distance only. Do NOT multiply attractiveness by bed count in the base formula: the secondary guide's gravity model does that, but the **primary plan does not**.
- A closed hospital can remain in the *baseline dependency* set: its closing should damage the district score before rerouting. The rerouting algorithm, separately, excludes it from receiving flow.

**IMPORTANT injection interaction:** `set_share(district,hospital,value)` is not a change to the hospital's physical location. It intentionally overrides a base share and must make the other eligible shares sum to 1, with a logged, deterministic redistribution rule. **IMPLEMENTATION DECISION:** redistribute the remaining `1-value` proportional to the others' previous shares; if the district has only one eligible hospital, its share must stay 1 unless eligibility is explicitly expanded. An injection that adds a new transfer candidate needs a separate **routing eligibility** modification, not just a dependency edge. Never pretend adding an FDNA hospital-hospital edge automatically grants a patient transfer agreement.

## 10. IL2: flow, capacity, injections, own scores

### 10.1 Inputs for one week

- End-of-week district epidemic occupancy `H_j` (people) from SEIR.
- Baseline catchment shares `s_ji` and allowed routing candidates.
- Per-hospital normal occupied **bed count** `B_i`.
- Per-hospital staffed capacity `C_i`.
- All injections active during the chosen week.

### 10.2 Calculate raw before-rerouting state

```text
flow_before[j,i] = s_ji * H_j
EpidemicDemand[i] = sum_j(flow_before[j,i])
TotalDemand[i]    = B_i + EpidemicDemand[i]
EffectiveCapacity[i] = C_i * capacity_factor_i
OwnScore[i] = 100 * min(1, EffectiveCapacity[i] / TotalDemand[i])
Excess[i]   = max(0, TotalDemand[i] - EffectiveCapacity[i])
```

**Safety handling:** If `TotalDemand=0` and effective capacity >0, own score =100. If hospital is explicitly closed, **own score=0 even if no demand**. If both demand and capacity are zero for a nonclosed facility, reject inconsistent input or use a documented convention; never divide by zero. Score injections cannot create more physical beds; store `physical_own_score` and `effective_own_score` (after explicit cap) separately when necessary.

**Critical unit rule:** `B_i` must be bed count; for an assumed baseline fraction `f`, calculate `B_i=f*C_i`. A score of 80 when demand=125 and capacity=100 means *capacity/demand proxy* 80%, NOT evidence 80% of actual patients were treated.

### 10.3 Graph construction (prior to FDNA)

Build one stable graph per week (or graph template with modified weights):

- Hospital nodes: `H:<hospital_id>`, with `own_i` as their exogenous physical upper bound.
- District nodes: `D:<district_id>`, with intrinsic baseline 100.
- Hospital-to-hospital links both directions when distance<=`hospital_link_radius_km`; default alpha_h=0.1 and beta_h=100, symmetric.
- Hospital-to-district links for every eligible `share>0`, with `beta_ji=100*(1-s_ji)` and the share-weighted strength described in Section 11; `alpha_d` is a **global district-level value**, not `alpha_d * share` passed into a subsequent mean.
- No hospital dependence on a district in FDNA; disease enters through `TotalDemand`.
- Topology and weights after active edge/share injections must be archived so results are reproducible.

### 10.4 Applying injections: validation and precedence

1. Select injections with `start_week <= week < end_week` (or no end).
2. Apply eligibility/share edits first (because they alter the base flow and district dependence); validate share sums.
3. Apply capacity/closure modifiers and explicit score caps; validate bounds.
4. Apply hospital-hospital dependency edits; keep symmetry unless the user deliberately selects and documents a directed override.
5. Build flows, loads, own scores, and graph; solve FDNA; then optionally reroute and recompute only the downstream weekly load/score calculations.
6. Log every applied injection in canonical sorted order with source, target, old/new value, active weeks, and warning if it overrides another injection.

**IMPLEMENTATION DECISION:** `set_score(value)` is implemented as a **cap on operability**, i.e. `min(physical_own_score,value)`; `reduce_score(amount)` lowers the score without going below zero. This models extra failures without allowing a score slider to conjure new beds. If the team needs an intentional score uplift above physical own score, add a separately named experimental override and a prominent nonphysical assumption warning; do not make that the default.

## 11. FDNA-based failure propagation

### 11.1 Original FDNA vs the project adaptation

Garvey and Pinto's 2009 FDNA paper uses a strength term for receiver `j` of `alpha_ij * P_i + 100*(1-alpha_ij)` averaged over feeders, and a criticality ceiling `min_i(P_i+beta_ij)`, then takes the minimum. The primary DS+X plan introduces **additional modeling choices**: hospital own capacity score as the receiver's baseline/cap, fixed-point iteration over two-way hospital edges, and a share-weighted district strength equation. It is therefore scientifically safer to describe our model as **"FDNA-based operability propagation"**, not an exact reproduction of unmodified classical FDNA.

### 11.2 Hospital iterative solve (supports symmetric cycles)

For each hospital `i`, own/effective physical score `O_i`, hospital neighbors `N(i)` and last iteration's scores `P_j`:

```text
if N(i) is empty:
    P_i_new = O_i
else:
    strength_ij = alpha_ij * P_j + (1 - alpha_ij) * O_i
    strength_i  = mean(strength_ij for j in N(i))
    critical_i  = min(P_j + beta_ij for j in N(i))
    P_i_new     = clip(min(O_i, strength_i, critical_i), 0, 100)

initialize P_i = O_i
synchronously update all hospitals using the PRIOR iteration vector
stop when max_i(abs(P_i_new - P_i)) <= 0.1 score points
```

`beta_h = 100` means the hospital-to-hospital criticality term is not binding for scores 0-100; the default effect arises from alpha_h. The `min(O_i, ...)` is the project's own-score cap. Initializing at O and using a monotone mapping ensures scores never increase from this initial vector under a fixed graph. Add a hard iteration safety cap and return convergence diagnostics; **do not silently return a nonconverged answer**. A warning or test failure must reveal nonconvergence.

**Implementation details:** compute all neighbor effects from the same prior vector (synchronous/Jacobi); using partially updated values in one pass changes results with hospital iteration order. Stable ID sort, float arithmetic, consistent tolerance and a high-resolution diagnostic are mandatory.

**Sanity check:** If two hospitals both have `O=100` and no injection, both remain 100. If one hospital closes (`O=0`) and the other is connected with alpha=0.1, beta=100, the closed node stays 0 and its neighbor can degrade under the shared-resource assumption. If alpha_h=0, *no hospital-to-hospital spillover remains*, while its district dependency damage may still occur.

### 11.3 District FDNA-based score (share-weighted)

For district `j`, with **unchanged baseline shares** `s_ji` and final hospital scores `P_i`:

```text
SOD_j = alpha_d * sum_i(s_ji * P_i) + (1 - alpha_d) * 100
COD_j = min_{i: s_ji>0}( P_i + 100 * (1 - s_ji) )
DistrictScore_j = clip(min(SOD_j, COD_j), 0, 100)
```

Criticality is a cap, not a direct subtraction from the health score. This is a modified, share-weighted FDNA-style rule. It must use post-hospital-cascade scores, not raw own scores.

### 11.4 Golden district checks from the primary DS+X plan

Assume alpha_d=0.9, one hospital with score 0 and all other eligible hospitals score 100:

| Eligible hospitals | Failed hospital's share | Strength term | Criticality cap | Expected district score |
|---:|---:|---:|---:|---:|
| 1 | 1.00 | 10.0 | 0.0 | **0.0** |
| 2 equally accessible | 0.50 | 55.0 | 50.0 | **50.0** |
| 4 equally accessible | 0.25 | 77.5 | 75.0 | **75.0** |

These are unit tests, not real Boston findings. With all hospitals at 100 the district score is 100 (not a derived healthcare outcome rate).

### 11.5 Invalid FDNA implementations

- A standard DAG solver that rejects hospital-hospital cycles is wrong for THIS default design; the secondary reference uses a DAG because it has a different model.
- Averaging the district's per-edge `alpha_d * share` terms and then weighting them again is wrong (double dilution).
- Using hospital `baseline_beds` as if it were an operability score is wrong (mixing units).
- Updating district scores before hospital fixed-point convergence is wrong.
- Using an incoming district -> hospital edge is wrong for v1.
- Calling the network node graph a validated real transfer network is wrong; proximity-based hospital-to-hospital ties are **assumed resource sharing**.

## 12. ANALYSIS: deterministic rerouting and accounting

### 12.1 What the algorithm is allowed to move

This model distributes `H_j`, the **current epidemic hospital census**. Rerouting therefore represents a hypothetical within-week redistribution of modeled hospital occupancy. It does NOT prove that moving already-hospitalized patients is clinically feasible. It does NOT relocate normal/non-epidemic baseline patients. These limitations must appear in the app.

**Goal:** Reduce excess by moving epidemic demand from overloaded hospitals to other *eligible* hospitals that have demonstrable spare effective capacity after counting their baseline and existing epidemic demand. Never exceed recipient capacity in the default rerouting policy.

### 12.2 Exact greedy procedure

1. Copy all before-flow and load arrays. Never edit the before snapshot in place.
2. `excess_i=max(0,B_i+sum_j flows[j,i]-Ceff_i)`. Sort overloaded hospitals by **descending excess**, tie-break by hospital ID.
3. For source hospital `h`, sort contributing districts by **descending `flows[j,h]`**, tie-break by district ID.
4. For each such district `j`, order alternative eligible hospitals `c != h` by **descending baseline `s[j,c]`**, tie-break by `(distance, hospital ID)`. An explicitly closed hospital is never eligible to receive demand.
5. Candidate spare capacity: `spare_c=max(0,Ceff_c-B_c-sum_j flows[j,c])`. If zero, try the next candidate.
6. Move `m=min(excess_h,flows[j,h],spare_c)` (positive finite float). Update `flows[j,h]-=m`, `flows[j,c]+=m`, recompute source excess and target spare, record `(j,h,c,m)`.
7. Continue until source's excess is zero, or no positive authorized move remains. Repeat over overloaded hospitals as requested in the plan, but terminate if a full pass makes no positive move.
8. Recompute every hospital's load, own score, hospital FDNA scores and district access score from the **after** flow table.
9. Calculate **unmet** using effective capacity and real post-rerouting demand. Do not make it zero merely because an assignment exists in the matrix.

**Algorithm termination:** A positive move comes only from an overloaded hospital and goes to a hospital with spare beds, so it reduces total positive overload and does not create new recipient overload. Add float epsilon to guard against tiny looping moves. No rounding patient counts to whole numbers inside iterative math; round only for display and reconcile decimal totals numerically. Keep every reallocation within the chosen week.

### 12.3 The critical demand-accounting correction

The primary plan informally states `served + rerouted + unmet = total demand`. That is only valid if `served` **excludes rerouted patients**. A common bug is to count rerouted patients in both served and rerouted, double-counting them. Use explicit disjoint categories:

```text
baseline_demand_total = sum_i B_i
epidemic_demand_total = sum_j H_j

per hospital:
    baseline_served_i = min(B_i, Ceff_i)
    baseline_unmet_i  = max(0, B_i - Ceff_i)
    epidemiology_capacity_i = max(0, Ceff_i - B_i)
    epidemic_demand_i = sum_j final_flow[j,i]
    epidemic_served_i = min(epidemic_demand_i, epidemiology_capacity_i)
    epidemic_unmet_i  = max(0, epidemic_demand_i - epidemiology_capacity_i)

MUST HOLD:
   baseline_demand_total + epidemic_demand_total
   = baseline_served_total + epidemic_served_total
     + baseline_unmet_total + epidemic_unmet_total

ALSO MUST HOLD:
   epidemic_demand_total = direct_served + rerouted_served + epidemic_unmet_total
```

`rerouted_served` is the moved amount **that reached spare capacity**, a subset of `epidemic_served`. It is NOT another independent demand category. The "rerouted count" KPI is an intervention volume, **not** the number of extra patients guaranteed to survive or the change in unmet demand. For a closing hospital, its non-epidemic baseline demand can be stranded; report `baseline_unmet_i` separately because there are no normal-patient origin districts in the input.

**Occupied beds versus demand (critical for validation):** `total_demand_i` is the attempted bed demand **before** capacity constraints. The modeled physical bed census *served* at hospital i in a selected phase is `predicted_occupied_beds_i = baseline_served_i + epidemic_served_i` (bounded by `Ceff_i`). Preserve and export BOTH fields. If the real HHS target is **total occupied beds**, compare it with `predicted_occupied_beds_i`, not silently with unconstrained demand. If the observed target is **COVID-only occupied beds**, compare it with `epidemic_served_i` for the matching historical hospital/week. This is an **IMPLEMENTATION DECISION** needed for units and target definition. These simplistic capacity constraints may not represent actual surge staffing or historical occupancy above nominal capacity; document this limitation.

**Per-district epidemic unmet:** Distribute each hospital's remaining epidemic-unmet amount among origin districts in proportion to their final epidemic demand at that hospital (or use an explicitly documented deterministic priority allocation). Then `sum_j epidemic_unmet_by_district[j] = sum_i epidemic_unmet_i`. Do not claim this is observed patient-level triage; it is an attribution for aggregate visualization.

### 12.4 Synthetic worked rerouting case (TEST ONLY)

Two hospitals, one district; all figures in this paragraph are **synthetic unit-test values**:

- Hospital A: capacity 100; baseline occupied 70; epidemic flow 50; demand 120, excess 20.
- Hospital B: capacity 100; baseline occupied 60; epidemic flow 10; demand 70, free 30.
- The district can use both hospitals. Move **20** from A to B.
- After: A demand=100; B demand=90; no residual excess. Epidemic census remains 60 total; exactly 20 is counted as rerouted and served; no one is invented or deleted.

Additional tests: make B free=5 -> move only 5, leave 15 excess; close A -> reroute its epidemic 50 where possible but flag A's baseline 70 as non-epidemic unmet; give a district no second eligible hospital -> no reroute, unmet remains.

### 12.5 Before/after definitions

- **Before rerouting:** all week injections applied, initial distance-share allocation, calculated scores and unmet. It is a counterfactual *within the same intervention scenario*.
- **After rerouting:** same injections and epidemic state, but redistributed epidemic flow with recomputed scores and unmet.
- **Baseline run:** zero user intervention injections, over all weeks.
- **Intervention run:** selected user injections, over all weeks.

A proper compare view must identify BOTH axes: `(baseline vs scenario)` and `(before vs after rerouting)`. The simplest UI defaults to the intervention scenario and toggles before/after; a second comparison panel compares baseline-after vs scenario-after for the same week. Never mix these four values into a misleading single toggle.

### 12.6 ANALYSIS acceptance gates

- For each district, its allocated epidemic demand across hospitals is exactly `H_j` both before and after (including the unmet portion still assigned to its origin hospital).
- No move to closed/ineligible/source-same hospital, no negative flows, no recipient demand exceeding capacity **due to a move**.
- No rerouting or graph updates mutate the SEIR compartment state.
- After rerouting, summed positive excess is nonincreasing, subject to float tolerance and with baseline demand held constant.
- When zero spare capacity exists, rerouted volume is zero and unmet is transparently positive.
- Score and unmet differences are calculated with the same input week, not the next time step.

## 13. Injections, scenario comparisons, and the weekly loop

### 13.1 Supported injection kinds

| Kind | Parameters | Effect | Validation / warnings |
|---|---|---|---|
| `close_hospital` | hospital ID, week interval | `capacity_factor=0`; own score=0; cannot receive reroutes | Must name existing hospital |
| `set_capacity` | hospital ID, nonnegative factor | Effective capacity = `C * factor` | 0..1 is closure/shortage; >1 represents **hypothetical added capacity**, annotate |
| `set_score` | hospital ID, 0..100 | Additional operability cap; see §10.4 | Cannot create physical bed capacity |
| `reduce_score` | hospital ID, 0..100 points | Subtract from operability cap, floor at 0 | Log prior and new cap |
| `add_edge` | hospital A/B, alpha, beta | Add **resource-dependency** link | Default paired two-way; not automatically a transfer route |
| `remove_edge` | hospital A/B | Remove dependency link(s) | Default paired two-way |
| `set_edge` | hospital A/B, alpha, beta | Change dependency weight(s) | Bounds enforced; log if asymmetric override |
| `set_share` | district, hospital, new share | Override **baseline** share and renormalize remaining shares | Must preserve sum=1 and authorized eligible set |

**Special case "add a transfer link":** The primary plan mentions a new transfer agreement as an example of an `add_edge`. That conflates a **dependency edge** with a **routing eligibility edge**, which this architecture otherwise keeps separate. **IMPLEMENTATION DECISION:** v1 supports `add_edge` strictly as a resource-dependency change. If the frontend promises an added transfer agreement, the agent MUST also implement and test a separately typed `add_route_option(district,hospital)` (or explicitly labeled `allow_transfer(source_hospital,target_hospital)`) operation that changes routing permissions, *without* automatically changing FDNA dependencies. Otherwise hide this control and list it as future work. **Never ship a link button that silently has no rerouting effect.**

### 13.2 Precedence, reversibility, timeline

- Injection has a stable UUID or stable explicit ID; start inclusive and end exclusive (e.g. start=3, end=5 affects weeks 3 and 4 only).
- Events are evaluated from the immutable **base config** each week, not by repeatedly multiplying capacity from the previous week. A factor 0.6 does not silently compound 0.6^t.
- If conflicting injections target the same property during the same week, either reject them with a useful UI error or apply a clearly defined last-wins order by explicit priority then ID. **Default safer rule:** reject contradictions except for documented `reduce_score` stacking.
- If an event ends, the affected parameter returns to its original base value for the next week; any epidemic state remains carried normally.
- A scenario reset removes user injections, not the raw data, historical calibration or fixed project assumptions.
- Export includes every active injection, applied value and its human-readable note, e.g. "MGH capacity reduced to 60% during weeks 4-7 (hypothetical)". Any real hospital named in an *invented scenario* must be clearly marked hypothetical.

### 13.3 Scenario comparison

For `compare_runs(base, scenario)`, require matched region, hospitals, districts, dates and base model settings; differences solely attributable to documented injections. Return per week:

- total epidemic unmet before/after, baseline non-epidemic unmet, overall excess;
- per-hospital effective capacity, demand, own score and final FDNA score;
- per-district before/after score, score change, unmet epidemic attribution, total accessibility and EJ flag;
- intervention count/volume and `rerouted_served`;
- worst affected hospitals/districts, with numeric sorting rules; and
- intervention effects relative to baseline-after (e.g. `scenario_after_unmet - baseline_after_unmet`).

Never use language "lives saved" or claim a capacity injection was implemented at a real facility. A change in a proxy score is a simulated change in a proxy score.

## 14. IL3: results, export, and orchestration

### 14.1 Weekly orchestrator contract

The orchestrator holds all run-level immutable setup, and for each `t in [0, weeks-1]`:

```text
PRECONDITION: validated real/synthetic inputs; fixed ID ordering; immutable config
PREP (once): DATA -> SEPARATE; build accessibility and base graph/crosswalk
for week t:
    starting_state = init_state(...) when t=0 else carry_state(previous_end_state)
    epi_output = SEIR.step_week(starting_state, config.disease)
    active_events = select_injections(all_events, t)
    before_inputs = IL2.build(epi_output.H, hospitals, accessibility, active_events)
    before_fdna = FDNA.solve(before_inputs)
    reroute_result = ANALYSIS.reroute(before_inputs)
    after_inputs = IL2.recalculate_loads_and_graph(before_inputs, reroute_result.flows)
    after_fdna = FDNA.solve(after_inputs)
    week_result = IL3.package_results(epi_output, before, after, reroutes, active_events)
    run_history.append(week_result)
    previous_end_state = IL3.next_state(epi_output)
validate_run_history(); export serializable results
```

The **before** and **after** FDNA passes do not mutate disease state. The next week's initial state is the SEIR output regardless of whether the user changes the before/after toggle. If the solver must rerun from week 0 on every config change to preserve chronology, do so and cache by config hash. With this model (no feedback), SEIR may be precomputed and reused for injections that only affect the network; only do so if the cache key and causal logic are proven correct.

### 14.2 Required per-week output

- A `WeekResult` with `week_index`, optional `week_start/week_end` dates, source mode, active injections and diagnostic status.
- `state_end` and per-district new infections, new admissions and hospitalized census.
- Before-and-after matrices of epidemic flows (not necessarily all returned to the UI by default; exports should offer them).
- Hospital rows including `baseline_demand_beds`, `epidemic_demand_beds`, `total_demand_beds`, `capacity_beds`, `predicted_occupied_beds`, `baseline_served_beds`, `epidemic_served_beds`, `physical_own_score`, `effective_own_score`, `fdna_final_score`, `excess_beds`, and separate baseline/epidemic unmet.
- District rows including `population`, `risk_weight`, `ej_flag`, `H_census`, `weekly_admissions`, `total_accessibility_index`, `district_fdna_score`, `epidemic_unmet_attributed`, and display-ready geometry ID.
- Reroute ledger, scores before/after, checks (`compartment_mass`, `share_conservation`, `patient_mass`, `iteration_convergence`) and any warnings.
- `run_id` or hash of normalized config + input-file checksums + algorithm version, so two identical results can be reproduced.

### 14.3 CSV/JSON exports

Export at least `run_metadata.json`, `hospital_week.csv`, `district_week.csv`, `reroute_week.csv`, `injections.json`, and validation metrics JSON **only if computed**. All tabular exports include `run_id`, `week`, `scenario`, `phase` (`before`/`after`), IDs, exact units and source mode. Use UTF-8. Float values must remain numeric in files; display rounding must not contaminate calculations. GeoJSON exports optionally add polygon fields keyed by tract ID but must not silently overwrite source geometries.

### 14.4 Performance and error handling

- The demo run needs to be responsive on a small-to-moderate number of tracts and hospitals. Do not invent a benchmark target as an achieved measurement; measure actual run times, document data sizes and cache results.
- Cache geometry/distance/catchment computations separately from disease model outputs. Only cache functions whose entire meaningful input is included in the key.
- Use actionable exception classes: `DataValidationError`, `MissingObservedData`, `InvalidInjection`, `FDNAConvergenceError`, and `ScenarioCompatibilityError` (names are proposals). Streamlit translates them into plain-language error messages, never a blank map or silent synthetic fallback.
- A bad optional EJ file should disable the overlay with an explanatory warning while leaving the core simulation usable; missing mandatory hospital or district data should prevent a real-mode run.

## 15. Historical validation and honest metrics

**This is a required DS+X deliverable, not optional polish.** The primary plan requires a substantial dataset, identifiable method, and numeric validation. A graph alone is not data science.

### 15.1 Target, time units and data alignment

1. Confirm actual HHS facility-level weekly records exist for the chosen Boston hospitals and historical wave; HealthData.gov metadata alone is insufficient.
2. Inspect columns/dictionary: observed COVID hospitalization census, total inpatient beds used, staffed-bed capacity, admissions may have different definitions, frequency, and missingness. Choose one **compatible** target; document exactly what was measured.
3. Match historical HHS facility identity to the hospital table with a reviewed CCN/campus mapping. If campuses are aggregated for simulation but separate in observations, aggregate *once* by the same canonical mapping. Reject unresolved crosswalks for evaluation.
4. Use one common week-start convention (e.g. HHS reporting Sunday-Saturday) across disease integration, census snapshots, baseline persistence and chart axis. State whether hospital observations are weekly average, weekly ending census or another aggregate; do not substitute one for another without a documented alignment method. If observations are a **weekly mean**, integrate/store the comparable *mean of the seven modeled daily census values* for evaluation; if observations are an **end-of-week snapshot**, compare the corresponding modeled end-week census. The primary UI still moves in weekly steps either way.
5. Compare **beds to beds**, not fractions to counts. If using percent occupancy, denominator must be the exact matched staffed-bed definition; primary metric remains **absolute error in occupied beds**. For the historical test, use the modeled **served occupied-bed census** as defined in §12.3, with COVID-only versus all-patient target semantics explicitly matched.
6. Ensure HHS data for historical hospital behavior were *not observed under this simulated rerouting intervention*. The rerouting-on curve is a **counterfactual**; agreement with observed hospital occupancy does not validate a real-world transfer policy.

### 15.2 Temporal train/test protocol

- Select a dated, consecutive historical wave with enough matched weeks and hospitals. Before fitting, write down the train and test windows in `validation-report.md`.
- Fit R0 (and perhaps pH) on **training weeks only** by least squares using the same documented model-to-observation operator that will produce test forecasts. Store fitted parameters and optimizer diagnostics.
- For every allowed test week `t`, produce a **t+1 prediction without fitting on that t+1 observation**. Use the same epidemic initialization/rollout convention throughout the test. The strategy (rolling one-week-ahead vs fixed-origin multiweek projection) must be named; they are not interchangeable.
- Persistence baseline for the same observed hospital/weekly keys: `forecast_naive[h,t+1] = observed[h,t]`. This is the plan's required baseline.
- Primary metric: `MAE = mean_{valid (h,t)} abs(predicted_beds[h,t+1] - observed_beds[h,t+1])` with all exclusions and the denominator `N` recorded. Compute baseline MAE over **exactly the same paired keys**.
- Also report coverage (`matched_hospitals`, `matched_forecast_weeks`, `n_pairs`), optionally per-hospital MAE and MAPE **only with valid denominators**. If the model loses, display both numbers accurately and say so.
- Optional comparison: rerouting enabled/disabled using exactly the same data/period. Label it "model ablation/sensitivity", **not proof** that hospitals actually rerouted patients.

### 15.3 Calibration and leakage safeguards

- Never use held-out future occupancy to set hospital baseline demand, fit R0/pH, choose peak dates, or select graph parameters for an evaluation that is described as "held out". If a pre-wave baseline is required, estimate it from training/preperiod observations only.
- Cross-hospital selection and facility mapping must not change opportunistically after seeing test errors. Document exclusions before reporting.
- If HHS observational data do not identify separate regional spread R0 and hospitalization pH, keep pH fixed at its labeled assumed value and fit fewer parameters.
- A county's observed hospitalizations include people who live elsewhere; district residents may attend hospitals outside Suffolk. Report this model/data mismatch, not precise tract forecasts.
- No statistical significance, calibration quality, error distribution, or historical event narrative should be fabricated. Tests involving mock data are labeled `synthetic_fixture`, and their "MAE" must never appear as observational validation.

### 15.4 Output schema for validation

```text
ValidationReport:
    status: verified | unavailable | incomplete
    target_variable: exact observed field, or null
    source_url: exact downloaded dataset URL, or null
    source_last_data_date: date or null
    training_start, training_end, test_start, test_end: dates or null
    reporting_week_convention: string
    matched_hospitals: integer
    forecast_pairs: integer
    fitted_r0: float or null
    fitted_p_h: float or null
    model_mae_beds: float or null
    persistence_mae_beds: float or null
    rerouting_off_mae_beds: float or null
    notes: list of limitations / exclusions
```

**UI rule:** If `status != verified` or `forecast_pairs == 0`, display no comparison numeric headline; render a neutral explanation with a link to provenance. A line chart may show illustrative model data only if clearly marked synthetic and never represented as a real backtest.

### 21.2 Four golden synthetic scenarios (not empirical results)

**S2 - two-hospital reroute:** Synthetic A capacity100/baseline70/H50, B capacity100/baseline60/H10; exactly 20 epidemic occupied beds shift A->B. End demand 100 and 90, total H60, total rerouted20, unmet0. Variant with B only 5 spare leaves 15 epidemic unmet.

**S3 - late closure injection:** Use 5 weeks with closure start=3, end=5. Baseline and intervention weeks 0-2 identical; in weeks3-4 the target has Ceff0 and own0; no reroute into it; since no feedback, SEIR compartments remain identical across both runs in every week. ### 21.3 Mathematical invariant tests (property-based if time permits)

For randomized small **synthetic** networks with nonnegative populations/capacities:

```text
0 <= S,E,I,R,H <= N  (within floating tolerance)
abs(S+E+I+R+H-N) <= documented mass tolerance
sum_i shares[j,i] == 1 for eligible j
sum_i flows_before[j,i] == H[j]
sum_i flows_after[j,i] == H[j]
0 <= all own/final district/hospital scores <= 100
sum H == direct_served + rerouted_served + epidemic_unmet
sum B + sum H == baseline_served + epi_served + baseline_unmet + epi_unmet
rerouted_volume <= sum H
moved flow only to legal positive-spare candidates
post-reroute total physical positive excess <= preroute positive excess
same input -> deterministic outputs
injection begins at t -> earlier weeks unaffected
when feedback disabled, disease state identical for all pure network injections
```

Use a numerical tolerance appropriate to data scales and float solver precision, not exact `==` for noninteger float sums. Tolerance must be documented, testable and never so large it hides a missing patient category.

## 22. Data quality, ethics, model limitations, and demo language

### 22.1 Ethics commitments preserved from primary plan

- **Privacy:** Public aggregate district/hospital metrics only; absolutely no patient-level record ingestion, health IDs, or identifiable individual routes.
- **Equity:** Show an EJ overlay to illustrate distribution of *modeled* access loss; do not infer a causal health-disparities estimate from an arbitrary EJ threshold or an assumed risk multiplier.
- **Transparency:** Put every assumed value in config and `docs/assumptions.md` / public README; document population denominator, geography, distance decay and crosswalk caveats.
- **Human consequences:** This is a sandbox planning simulation. It cannot decide ambulances, real patient transfers or hospital closures.
- **Quality:** Avoid precise false accuracy. Round readable UI labels, but preserve numeric data for computation and export.

### 22.2 Model limitations to state on-screen

1. **Suffolk is not a closed hospital catchment:** Boston hospitals treat patients from outside Suffolk, and Suffolk residents may attend hospitals outside the chosen list. This affects calibration and overflow estimates.
2. **Proximity is not a real referral/transfer network:** Hospital shares are derived from straight-line kilometers, not ambulance dispatch, road travel time, insurance, specialization, network affiliation, preference or formal agreements.
3. **Uniform regional epidemic in Option A:** The basic model has no observed neighborhood-to-neighborhood transmission and no age-stratified disease severity; risk weights are hypothetical or observationally linked proxies.
4. **Beds alone oversimplify capacity:** Staff, specialty, ICU availability, oxygen, infection-control limits, equipment and service type are not modeled as resource nodes in this v1. Hospital staffed-bed data are not necessarily the same as licensed/physical bed counts.
5. **Unmet is a simplified capacity gap:** It does not measure deaths or real ambulance refusal, and can include an immovable non-epidemic baseline at closed hospitals. Rerouting assumes transfers can happen without delay/cost.
6. **FDNA weights are assumptions:** α_h, beta_h, alpha_d and criticality mapping have not been fitted to empirical hospital resource-sharing dependencies. It's a **FDNA-based adapted model**.
7. **No behavioral feedback:** Unmet demand, closures and rerouting do not feed back to infections or deaths, by explicit primary-plan default.
8. **Historical validation limitations:** HHS facility data are historical (reporting ended 2024); facility-level census may reflect people from a much larger geographic area than simulated Suffolk. An out-of-sample error metric evaluates that proxy target under stated alignment, not the realism of every intervention.
9. **Visualization fairness:** Tract population size can vary. Showing each tract equally in a ranked list is not the same as population-weighted access loss. Report the denominator and allow sorting by population/unmet where helpful.
10. **Mode labels:** A run with real map geometry but assumed epidemic, hospital shares or FDNA weights is still a **scenario**, not an observed state of Boston.

### 22.3 Prohibited marketing statements

Do not write "real-time hospital monitoring", "life-saving recommendations", "proven optimized transfers", "validated medical model", "predicts hospital closures", or "improves equity" without defining the exact measured or simulated proxy and supporting evidence. The name ResiliNet does not imply regulatory/clinical approval.

Opening can be grounded without an unsupported single statistic:

ResiliNet is an educational Boston-area what-if simulator: a simplified SEIR epidemic model estimates demand; a FDNA-based network maps hypothetical operability losses; and a capacity-aware rerouting step tests whether spare beds would reduce the modeled shortfall.
